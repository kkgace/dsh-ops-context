# dsh-context-lite-macos 0.2.0 量化报告 v4 —— 节省目标达成验证

**测试对象**：本机 DSH 运行实例（进程 01:40:11 启动 > 0.2.0 安装，确认运行代码=磁盘代码）
**测试用例**：与 v3 完全相同（语料 bench-corpus2、任务书 T1–T4 逐字一致、日志 1:1 落盘、tiktoken 精确计数 + projcache 真实 API usage）
**单测**：20/20（新增同行聚合、凭据名可见、全量自证三组回归）

---

## 1. 结论先行

**同样测试用例下，插件组任务级总成本从 0.1.1 的 442,228 token 降至 0.2.0 的 37,419 token，节省 91.5%，达成 ≥70% 目标**；且正确性从"漏 2 处 + T4 失败"提升为"全部正确（含 T4 凭据文件名）"。

## 2. 0.2.0 做了什么（针对 v3 实测的三大成本根因）

| v3 实测根因 | 0.2.0 改动 |
|---|---|
| 同行多次出现需逐字读取核验（T1 引发多次调用） | 同行命中合并为一条并标注 `×次数`（`bundle.js:1(×3)`） |
| "搜索不完整"不可定位 + 100 行预算截断引发补偿扫描 | 预算放宽至 400 文件/400 行/60 匹配/16,000 字符 + **全量扫描自证标记**（`[全量扫描：5 个文件、5 个目录，共 5 处命中，无遗漏]`），一次调用即完整答案 |
| 凭据文件完全不可见 → 11 次盲枚举 | 隐藏/凭据**文件名可见、内容必拦截**（`[隐藏/凭据文件（仅列出文件名，内容一律不读取）：app/.env.local、app/id_rsa]`） |

## 3. 同用例对照数据

### 3.1 主口径：插件版本演进（0.1.1 → 0.2.0，同任务书同语料）

| 指标 | 0.1.1（v3 实测） | 0.2.0（本轮） | 节省 |
|---|---:|---:|---:|
| 任务级 uncachedInputTokens | 352,166 | 20,805 | 94.1% |
| 任务级 outputTokens | 90,062 | 16,614 | 81.6% |
| **任务级总量** | **442,228** | **37,419** | **91.5% ✅** |
| 信息获取调用次数 | 26 | 5 | 80.8% |
| 正确性（对照 ground truth） | T1 漏计/不可计数、T4 失败 | T1–T4 全对 | — |

### 3.2 次口径：跨工具箱（同轮 A''原生 vs B''插件，两组各 5 次调用）

| 指标 | A'' 原生 | B'' 插件 0.2.0 | 差异 |
|---|---:|---:|---:|
| 工具交付总量（tiktoken cl100k） | 1,175 | **904** | **−23.1%** |
| 单次最贵调用 | 353 | **311** | −11.9% |
| 任务级 uncachedInput | 26,824 | 20,805 | −22.4% |
| 任务级 output | 10,935 | 16,614 | +52.0%（模型 thinking 量，工具不可控） |
| 任务级总量 | 37,759 | 37,419 | −0.9%（持平） |

**诚实边界**：本轮 A 组也只用了 5 次调用（聪明模型 + 小语料的强基线），其工具交付仅占任务级总成本的 3.1%——在此用例上，"跨工具箱省 70%" 数学上不可达（即使插件交付降为 0，任务级也只省 2.4%）。剩余 97% 是框架步数开销与模型 thinking，不属于工具可控范围。跨工具箱 70% 的成立场景是**工具交付占比高的用例**（大文件/压缩 bundle/贪婪读取），即 v1–v3 已证明的 31–99.7% 单次封顶价值。
