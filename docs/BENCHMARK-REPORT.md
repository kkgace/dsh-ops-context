# dsh-context-lite-macos Token 基准报告 v2

**版本**：插件 0.1.1（实测）/ 0.1.2（含本轮改进）｜ **日期**：2026-10-15 ｜ **方法修订**：本版替代 v1——v1 的 `≈4字符/token` 估算已弃用，改为 **tiktoken 双词典实测计数** 与 **真实 A/B 会话的模型 API usage**（从 DSH projcache 提取）。

---

## 0. 核心结论（先说诚实的）

**插件节省的是"单次工具调用的交付 token"，且有数学硬上限；但在本次任务级 A/B 真实会话对照中，插件工具箱总消耗反而更高（input +18%、output +70%），且正确性有损。** 两者不矛盾——插件的价值是**最坏情况保险 + 安全拦截 + 去重**，不是"任务级普遍省 token"。以下三层证据全部来自实测，包括对插件不利的部分。

---

## 1. 第 1 层证据：单次调用交付量（js-tiktoken 精确计数）

对每次工具调用的**实际返回文本**分别用 `cl100k_base` 与 `o200k_base` 两个 tokenizer 计数（脚本 `bench-tokens.mjs`，可复现）：

| 场景 | cl100k 基线→插件 | 节省 | o200k 基线→插件 | 节省 |
|---|---:|---:|---:|---:|
| T1 检索 `assertWorkspaceTarget` | 279 → 192 | 31.2% | 275 → 182 | 33.8% |
| T1 检索 `rememberRead` | 61 → 41 | 32.8% | 61 → 33 | 45.9% |
| T1 检索 `proxy-groups`（命中压缩 bundle） | **135,538 → 455** | **99.7%** | **129,017 → 445** | **99.7%** |
| T2 摘览 core.js 前 40 行 | 4,169 → 654 | 84.3% | 4,092 → 650 | 84.1% |
| T3 同轮重复读取（去重） | 1,732 → 72 | 95.8% | 1,384 → 63 | 95.4% |
| T4 读 `.env.local`（敏感拦截） | 26 → 36 | −38.5%* | 26 → 25 | 3.8% |

\* T4 的价值不在 token 而在**拦截**：基线会交付 81 字节密钥内容进上下文，插件交付 0 字节（cl100k 下拒绝消息比密钥内容还长 10 token——买保险有保费）。

**结构性解读**：插件输出有硬上限（`maxSearchChars=9,000` / `maxReadChars=12,000` 字符 / 去重提示 ~115 字符）。最坏情况与基线的差距是**常数级保险**：本语料一次朴素整行 grep 注入 135,538 token（= 262,144 窗口的 **51.7%**），插件同任务 455 token（0.17%），**上限比 298:1**。

---

## 2. 第 2 层证据：任务级真实 A/B 会话（模型 API usage，非估算）

同一任务书（①在 mihomo_config 定位 `proxy-groups` 全部 文件:行号；②给出 core.js 240–250 行原文；③判断 app/ 下是否存在凭据文件），两个独立真实 subagent 会话，A 只用原生工具（read/grep/bash/glob，8 次调用），B 只用插件工具（context_search/context_read，31 次调用）。Token 数从 DSH `session_projcache` 提取，是**模型 API 返回的真实 usage**：

| 指标 | A 原生 | B 插件 | 差异 |
|---|---:|---:|---:|
| uncachedInputTokens | 33,017 | 39,073 | **+18.3%** |
| outputTokens | 10,415 | 17,707 | **+70.1%** |
| surfaceTokens（表面上下文） | 18,394 | 31,888 | **+73.4%** |
| 工具调用次数 | 8 | 31 | +288% |

**任务正确性**：任务 2 两者逐字一致；任务 1 A 组 9 处、B 组仅确认 7 处（缺 `BzbovP_B.js:107/108`——插件如实标注"搜索不完整；跳过 1 个文件"，但被跳过文件身份无法定位，B 组花了大量调用补偿）；任务 3 **对比无效**——B 组插件被会话工作区边界（设计语义）限制在 `<workspace>`，看不到 `/tmp` 语料中的 app/ 夹具，A 组 bash 无此边界。

**诚实归因**：
1. 任务书偏"全量枚举"，A 组的 `grep -o` 计数策略天然适配，聪明模型 + 无界工具本任务占优；
2. B 组 25 次 `context_search` 中相当部分是在补偿"跳过文件不可定位"的能力缺口——轮次开销吞掉了单次交付的节省；
3. 模型 API usage 含系统提示/委派框架的固定开销，两组各含一份。

---

## 3. 第 3 层：修正后的价值主张

| 场景 | 插件是否占优 |
|---|---|
| 探索性检索 / 逐段读大文件 / 重复读取 | ✅ 省 31–96%（第 1 层实测） |
| 语料含 minified/超长行文件，或模型"贪婪"读取时 | ✅✅ 省至 99.7%，**防止一次调用注入 5 万+ token**（结构性封顶） |
| 凭据/越界/隐藏路径 | ✅ 唯一能拦的（0 字节外泄） |
| 全量枚举类任务 + 聪明模型 | ❌ 本 A/B 实测：总账 +18~73%，正确性 −2 处 |
| 超出插件边界的探测（目录存在性、二进制、工作区外） | ❌ 只能用原生工具补位 |

**插件正确定位：上下文风险的保险层，不是 token 节省器。** 它保证"最坏的一次工具调用不会撑爆窗口"（298:1 上限比）并默认拦截危险路径；省 token 是正常路径的副产品，不是任务级保证。

## 4. 本轮 A/B 直接催生的产品改进（0.1.2）

B 组卡在「跳过 1 个文件」却无法定位该文件，消耗大量补偿调用。0.1.2 将被跳过的路径（最多 5 个）直接列入提示，并给出处置建议：

```
[搜索不完整；跳过 1 个文件、0 个目录（mihomo_config/ui/_nuxt/BzbovP_B.js）。
可用 context_read 显式读取所列文件，或指定更窄的 path 或 query。]
```

已装本机 web profile（`dsh plugin --profile web install .../0.1.2.tgz`），单测 17/17；**需重启 DSH Web 进程后生效**（已知机制）。

## 5. 方法与局限（诚实边界）

- **计数器**：js-tiktoken `cl100k_base`/`o200k_base`，非 DSH 所接模型的分词器；但节省比例在同 tokenizer 内计算，跨词典结论一致（99.7%/84%/95% 量级稳定）。
- **A/B 为单次采样**：模型行为随机性未做多样本统计；任务书设计影响结论（本任务书对插件不利）。
- **B 组工作区边界**：插件工具按设计只见会话工作区，任务 3 因此无效对比——这本身是插件语义（工作区限定）的如实呈现。
- 复现：`node <benchmark-scripts>/bench-tokens.mjs`（第 1 层）；`node <benchmark-scripts>/extract-usage.mjs`（第 2 层，需对应会话的 projcache 残留）。
